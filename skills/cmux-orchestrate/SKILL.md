# cmux-orchestrate — cmux のペインで並行実装を回すオーケストレーター

## 流れ

```
0 前提の確認 → 1 計画 → 2 了承 → 3 準備 → 4 起動 → 5 監視と解説
  → 6 レビュー（オーケストレーターが各セッションの差分を） → 7 動作確認（1 本ずつ）
  → 8 説明（explainer） → 9 承認の後に commit ＋ push ＋ PR（マージの順に待ち合わせる）
```

## 作業の単位（タスク）とチケット

- 並行させる 1 単位を **タスク** と呼ぶ。1 タスク = 1 worktree = 1 ブランチ = 1 ペイン = 1 PR
- **チケットは任意。** 入力は次のどちらでもよい
  - **チケットがある**: チケットを読み、1 チケットを 1 タスクにする（大きいチケットは分けてもよい）。タスク ID はチケットの番号（例: `1234`）
  - **チケットが無い**: ユーザーの依頼文（と会話・リポジトリ）から、オーケストレーターがタスクに分ける。タスク ID は `t1`・`t2` …（例: `t1-login-rate-limit`）。チケットが要るかは了承のときに聞き、作るとしても了承の後に作る
- タスク ID は、worktree・ブランチ・指示書・ステータスファイルの名前に入れる。どの作業かを名前だけで見分けるため

## 役割の分担

| 誰 | やること | やらないこと |
|---|---|---|
| オーケストレーター（このセッション） | 計画・重なりの洗い出し・準備・起動・監視・解説・**各セッションの差分のレビューと指摘の送り返し**・収束・explainer での説明 | 実装コードを書く・指摘を自分で直す・コミットする |
| ワーカー（cmux の各ペインの Claude） | 指示書どおりに 1 タスクを実装・検証し、「レビュー待ち」で止まる。届いた指摘を直し、検証をやり直して報告する | 自分の差分を自分でレビューして完了にする・担当外のファイルを変える・コミット/プッシュ/PR・外部への書き込み |
| ユーザー | 計画の了承・各ペインの許可の確認・判断待ちへの答え・コミットの了承 | — |

## 手順

### Phase 0: 前提の確認

1. `cmux identify` で cmux の中にいることと、自分の `surface` を確かめる（cmux の外なら止めて伝える）
2. **PJ のプロファイルを読む**（[references/profile.md](references/profile.md)）。PJ のしきたり（検証・レビュー・設計書の同期・コミットの規約・禁止事項など）で判断するため
   - 置き場は **既定で git 管理外の `~/.claude/cmux-orchestrate/profiles/<PJ 名>/`**（`profile.md`・`config.yml`・`digest.txt`）。公開してよい PJ だけ、この skill の `profiles/<PJ 名>/`（git 管理）にも置ける。PJ 名はメイン checkout のフォルダ名（`bash scripts/harness-digest.sh name`）
   - 有れば `bash scripts/harness-digest.sh diff <置き場>/<PJ 名>/digest.txt` で、ハーネスが変わっていないか見る。変わったファイルがあれば、その分だけ読み直して直す
   - 無ければ、サブエージェントでハーネスを走査して作り、**ユーザーに見せて確かめてから**保存する。どちらの置き場にするかも聞く（答えが無ければ git 管理外）
   - リポジトリに `.claude/cmux-orchestrate.yml` があれば、`config.yml` よりそちらを優先する
3. ローカルの base ブランチが origin より遅れていないか確かめ、遅れていれば `git fetch` して **origin の base から切る**

### Phase 1: 計画（ここまでは何も作らない）

1. 入力を読む
   - **チケットがある**: 本文・AC・親・関連チケットを読む（読み方は設定の `tickets.show`）。関連チケットに同じ問題を扱うものがあれば、重なりと前後関係を示す
   - **チケットが無い**: 依頼文から、何を・なぜ・どこまでやるかを読み取る。読み取れないこと（範囲・完了の基準）は、計画の前に 1 回だけまとめて聞く
2. タスクに分ける。タスクごとに **目的・やること・しないこと・完了条件**（チケットがあれば AC、無ければオーケストレーターが書く。テストや計測で確かめられる形にする）を書く。並行できないほど絡むものは、1 タスクにまとめるか、順番に回す
3. タスクごとに、触るファイル・設計書の節・共有リソースを洗い出し、**重なり表**を作る。[references/overlap-checklist.md](references/overlap-checklist.md) の観点を全部見る
4. タスク間の**境界の約束**を決める（例: 新しい関数の名前と型・誰がどの行を触るか・後から足す呼び出しはどのブランチで入れるか）
5. **ブランチの形とマージの順**を決める。squash merge のリポジトリでは積まない（全部 base から独立に切り、後から入る方が rebase する）
6. 計画をユーザーに示す。タスクの一覧（ID・目的・完了条件）・重なり表・マージの順を並べ、決めてもらうこと（担当者の付け替え・チケットを作るか・外部からの素材の取得・並べる本数）を最後に並べる

### Phase 2: 了承

ユーザーの了承を取る。担当者の変更・チケットの作成など外部への書き込みは、了承の範囲を確かめてから行う。

### Phase 3: 準備

1. worktree を作る（ディレクトリとブランチの両方にタスク ID。命名は設定の `worktree.dir`・`branch`）。初期設定のコマンドを回し、**結果の表示を信じず、必須の成果物があるかを自分で確かめる**（[references/pitfalls.md](references/pitfalls.md) の「初期設定が黙って失敗する」）
2. 置き場 `<orchestration_dir>`（既定 `<worktree の親>/<作業名>-orchestration/`）を作り、次を置く
   - `common.md`: [templates/common.md](templates/common.md) を埋める（並行セッションの表・境界の約束・守ること・素材・報告の形）
   - `sN-<タスク ID>.md`: [templates/brief.md](templates/brief.md) を埋めたタスクごとの指示書（チケットが無いときは、Phase 1 で書いた目的・完了条件をそのまま入れる。ワーカーが読むのは指示書だけになるため、背景を省かない）
   - `status/`: ステータスファイルの置き場
   - `with-lock.sh`: 共有リソースがあるとき、[scripts/with-lock.sh](scripts/with-lock.sh) をコピーし、`PREPARE` を設定する
3. 共有のロックを無害なコマンドで 1 回通し、動くことと 1 回あたりの所要時間を確かめる。**ユーザーの手元の環境を変える（例: 起動中のコンテナを付け替える）なら、その旨と戻し方を伝える**

### Phase 4: 起動

[scripts/launch-panes.sh](scripts/launch-panes.sh) を使う（または同じ手順を手で）。

0. **ワーカーのモデルは、プロファイルの `config.yml` の `workers.model`（タスクごとは `workers.per_task`）で決まる。** `launch-panes.sh --config <config.yml>` が読んで `claude --model` に渡す（プロンプトで聞かない・決定論的にする）
   - `workers.model` が無いときだけ、起動の前にユーザーに聞き（そのとき使える最新のモデルと「指定しない」）、答えを `config.yml` に書いてから起動する
   - 組織の設定（`~/.claude/remote-settings.json` など）でモデルが固定されていても、起動時の `--model` が上書きする（2026-10-09 に `claude -p --model …` で確認）。設定の `model` や `/model` だけでは、新しく起動したセッションは組織の固定に戻る
   - 起動した後に変えるときは、そのペインに `/model <名前>` を送る（ユーザーの了承の後）
1. 自分の surface の右に 1 つ、そこから下に分割して本数分のペインを作る（`--focus false`）
2. 各ペインのタブ名を「S1 <タスク ID> 要約」にする
3. `cmux send` で「worktree に cd → `claude '<common.md> と <指示書> を読み、その指示に従って作業してください。ステータスは <status/> に書いてください。'`」を送り、`send-key Enter`
4. `cmux read-screen` で全ペインが指示書を読み始めたことを確かめる
5. ユーザーに、許可の確認は各ペインで直接応えるよう伝える（オーケストレーターは推奨を出すが、キーは押さない。Phase 5 の 2）

### Phase 5: 監視と解説

1. Monitor で [scripts/watch-status.sh](scripts/watch-status.sh) を張る（30 分で切れるので、切れたら張り直す）
2. 許可の確認も Monitor で [scripts/watch-permissions.sh](scripts/watch-permissions.sh) を張って見る。確認が出たら、そのペインの画面を読み、**推奨（許可 ／ 拒否 ／ 迷う）と理由**をユーザーに出す。キーは送らない（決めるのはユーザー。オーケストレーターが押すと、許可の仕組みを素通りすることになる）
   - 許可を推す: 自分の worktree の中の読み書き・テスト・ロック付きの入口からの検証・スクラッチでの計測など、指示書の範囲に収まるもの
   - 拒否を推す: ロックを通さない共有リソースの操作・ほかの worktree への書き込み・コミットやプッシュ・外部への書き込み
   - 拒否されたら、そのワーカーに理由と代わりのやり方を送る
   - cmux の Feed（`cmux feed tui`）にカードが届く環境なら、そちらで答えてもらってもよい（[references/pitfalls.md](references/pitfalls.md) の「Feed にカードが届かない」）
3. 段が変わるたびに、ステータス・`git status`/`git diff --stat`・要の差分を読み、次の形で解説する
   - **やっていること**（何を変えたか・どこまで進んだか）
   - **目的**（どの AC・どの問題に効くか）
   - **注目点・気にしている点**（設計の判断の良し悪し・後で確かめること）
3. 指示書と違う進め方（テストを飛ばす・担当外のファイルを変える）を見つけたら、差分で事実を確かめてから、そのペインに `cmux send` で指示を足す。指示書に追記した場合も、同じペインに知らせる
4. 「判断待ち」になったら、内容を要約してユーザーに諮り、返事をそのペインに送る。急ぎのものは PushNotification も出す
5. **ワーカーの結論（特に「要らない」「問題ない」）は、測っていない形が残っていないかを見てから受け取る。** 実際の使われ方に近い形が抜けていれば、追加の計測を指示書に追記して頼み直す（実例: あるタスクは「同じ対象を繰り返し直す」形だけを測って「不要」としたが、「別々の対象を順に直す」形で増えることが分かり、必要に変わった）

### Phase 6: レビュー（オーケストレーターが各セッションの差分を）

**レビューはオーケストレーターが行う。** ワーカーは検証が通ったら「レビュー待ち」で止まり、自分ではレビューしない。理由は 2 つ。

- 書いた本人のセッションは、自分の前提（指示書の読み違い・測っていない形）を疑いにくい。今回の実例でも、ワーカーの「不要」「対処済み」を外から見て覆した
- オーケストレーターだけが、セッション間の観点（境界の約束・同じ節の書き換え・マージの順）と、ほかのセッションの計測の結果を持っている

手順:

1. ワーカーの段が「レビュー待ち」になったら、そのブランチの差分（`git -C <worktree> diff <base>...HEAD` と作業ツリーの変更）・ステータス・指示書を材料にレビューする
   - 差分が大きいときや、言語・層の専門の観点が要るときは、リポジトリの code-reviewer 系のエージェント（無ければ一般の code-reviewer）をサブエージェントで回す。複数のセッションが同時に待っていれば、セッションごとに並列で回す。サブエージェントの指摘は、オーケストレーターが差分で裏を取ってから採る
   - オーケストレーター自身は、次の観点を必ず見る（サブエージェントに任せない）
     - 指示書の「やること」「しないこと」と AC が満たされているか
     - 境界の約束（関数の名前と型・触る行の分け方）と、ほかのセッションとの重なり
     - ワーカーの結論が、測っていない形やほかのセッションの結果と食い違っていないか
     - リポジトリの約束（例: ログの言語・設計書の同期）
2. 指摘を CRITICAL・HIGH・MEDIUM・LOW に分け、**そのペインに `cmux send` で送る**（長いときは `<orchestration_dir>/review/<番号>.md` に書き、そのパスを送る）。ユーザーには、解説の形（やっていること・目的・気にしている点）で同じ内容を伝える
3. ワーカーは、CRITICAL・HIGH は必ず直し、MEDIUM はできる範囲で直す。直さないものは理由をステータスに書く。直したら検証をやり直し、もう一度「レビュー待ち」にする
4. 指摘がほかのセッションの範囲に及ぶときは、どのセッションで直すかをオーケストレーターが決めて、そのペインに送る（ワーカーどうしで直接やり取りさせない）
5. 指摘が残らなくなったら、オーケストレーターがそのペインに「完了にしてよい」と送る。ワーカーはそれを受けて、段を「完了」にして完了の報告を書く

### Phase 7: 動作確認（タスクごと・1 本ずつ）

レビューが通ったタスクから、ユーザーに実物で確かめてもらう。

1. **1 本ずつ行う。** サーバ・コンテナ・ポートは 1 組を取り合うため。確認している間は、共有リソースのロックをオーケストレーターが握り、ほかのワーカーの検証がサーバを付け替えないようにする（`lockf -k <lock_file> sh -c '… フラグのファイルができるまで待つ …'` を裏で回し、終わったらフラグを作って放す）
2. **サーバの起動の仕方はプロファイルから読む**（`profile.md` の「共有リソースと環境」・`config.yml`）。**Docker とは限らない**（host のプロセス・`pnpm dev`・`uv run` など）。読み取れなければユーザーに聞く
3. ほかの checkout で同じサーバが動いていれば、ユーザーの了承を取って止める。そのタスクの worktree でサーバを起動し、**そのタスクのコードが載っていること**を確かめる（コンテナならマウント元、host なら起動したディレクトリ。足したコードが入っているかを 1 つ grep する）
4. 準備ができたら、**[templates/verification-checklist.md](templates/verification-checklist.md) の形どおりに**動作確認リストを出して、確認を依頼する。形は固定（対応した内容 → 環境 → 手順 → 確かめること）。環境の欄は必ず出す
5. ユーザーが貼ったログや画面の結果を、一緒に見て妥当かを答える。NG なら、そのワーカーに指摘として送り、Phase 6 に戻す
6. OK をもらったら、**サーバを落とし、元に戻す**（プロファイルの `restore_hint`。例: メイン checkout でサーバを起動し直す）。ロックを放す

### Phase 8: 説明（explainer）

動作確認が OK になったタスクについて、**実施したこと（変更とその理由）を explainer skill で速習資料にし、承認を依頼する。** エージェントが書いた量に、人の理解が追いつかないのを埋めるため。

1. explainer skill を使う（リポジトリにプロジェクト版があればそちら、無ければグローバル版 `~/.claude/skills/explainer/`）。その skill の手順（ペルソナ → 問い → 差分 → 実物 → 書く → 図 → 検証）に従う
2. 資料はタスクごとに 1 本（関係の深いタスクはまとめてもよい）。slug は `<リポジトリ名>-<タスク ID>-<要約>`（例: `myrepo-1234-login-limit`）。章立てが要るほど長くなるなら `explainer-book` を使う
3. 材料はワーカーの完了の報告・差分・レビューの記録・動作確認の結果。次を必ず入れる
   - 何が問題だったか（測った値）と、何をどう直したか
   - ほかのタスクとの関係（境界の約束・マージの順・後から足すもの）
   - 計測や判断で結論が変わった所（例: 「不要」→「必要」）とその根拠
   - まだ確かめていないこと（未検証）と、次の作業
4. 本文に引用するコード・出力・数値は、差分とステータスファイルから写し、explainer の検証（`verify-doc.mjs` が VERIFIED）に通す
5. **資料のファイルのパス（HTML の `dist/index.html`）と 3 行の要約を共有し、承認を依頼する**。直しの依頼があれば資料かコード（Phase 6 へ戻す）を直す

### Phase 9: 承認の後に commit ＋ push ＋ PR（マージの順に待ち合わせる）

1. **commit と push は同じタイミング**で行う（承認の前に commit しない。動作確認や説明の後に直しが入ることがあるため）。メッセージはワーカーの案を、リポジトリの規約（commitlint など。プロファイルの「コミット・PR・ブランチ」）に合わせて直す
2. **push の順はマージの順に合わせる。** 先に入るべきタスクがあれば、**そちらが Phase 9 に来て push を終えたのを確かめてから** push する。待つ間は、そのタスクは「push 待ち」としてユーザーに見せる
   - 後から入る枝が先の枝の変更を取り込むときは、リポジトリの決まり（例: `git merge origin/<base>`。push 済みの枝は rebase しない）に従う
3. **PR も push と同時に作る。** 作り方はプロファイルから読む（例: GitHub は `gh pr create`、Azure Repos は `az repos pr create` やリポジトリの PR 用の skill）。base・テンプレート・チケットのつなぎ方もリポジトリの決まりに合わせる
   - **PR を作れる環境が無いとき**（CLI が無い・ログインしていない）は、リポジトリ（リモートの URL・CI の定義・PR 用の skill）から使うツールを読み取り、入れる CLI とコマンドを示して了承を取ってから入れる。ログインが要るなら、ユーザーに `! <ログインのコマンド>` を打ってもらう
4. PR の URL をユーザーに渡す。全部の PR が出たら片付け（ペインを閉じるか聞く・worktree はマージ後に消す）
5. 最後に、今回詰まった点を [references/pitfalls.md](references/pitfalls.md) に足す（この skill の育て方）
