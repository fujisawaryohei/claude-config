## 進み具合の報告（オーケストレーターが読む）

`{{orchestration_dir}}/status/<タスク ID>.md` を、**段が変わるたびに上書きする**。形式は [status.md](status.md)。

判断が要るときは、段を「判断待ち」にしてから、次の通知を出して止まる。

```bash
bash {{orchestration_dir}}/notify.sh "<タスク ID> 判断待ち" "<一行で>"
```

## レビュー待ち（完了の前に必ず）

**レビューはオーケストレーターが行う。自分の差分を自分でレビューして完了にしない。**

1. 実装・設計書・検証が通ったら、段を「レビュー待ち」にし、ステータスに「完了の報告」と同じ内容（下）を先に書いておく。そのうえで次の通知を出して止まる
   ```bash
   bash {{orchestration_dir}}/notify.sh "<タスク ID> レビュー待ち" "<一行で>"
   ```
2. オーケストレーターから、指摘がこのペインに届く（長いときは `{{orchestration_dir}}/review/<タスク ID>.md` のパスが届く）
3. CRITICAL・HIGH は必ず直す。MEDIUM はできる範囲で直す。直さないものは理由を書く
4. 直したら、検証を回し直し、ステータスの「レビュー」の節に、届いた指摘・直したもの・直さなかったもの（理由）を書いて、もう一度「レビュー待ち」にする
5. 指摘がほかのセッションの範囲に及ぶと思ったら、直さずにそう書いて「判断待ち」にする
6. オーケストレーターから「完了にしてよい」と届いたら、段を「完了」にする

## 完了の報告

段を「完了」にし、次を書く: 変えたファイル／測った値／検証のコマンドと結果（落ちたものは出力付き）／設計書のどこを直したか／レビューの結果（届いた指摘と対応）／コミットのメッセージの案／完了条件（チケットの AC、または指示書の完了条件）ごとの自己点検（満たしたか・どう確かめたか）

この報告は、オーケストレーターが最後に explainer で速習資料にする材料になる。測った値・判断の理由は、後から読んで分かるように書く。
