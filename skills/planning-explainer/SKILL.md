# planning-explainer

実装プランは文章と表で書かれるので、**どの層が、どの順で、何を呼ぶか**が読み手の頭の中でしか組み立たない。
レイヤーごとに色分けしたシーケンス図にすると、変わるところ（【新規】【変更】）と、変わらずに使い回すところが一目で分かる。
また、図に描こうとすると「この関数は本当にこの順で呼ばれるか」を確かめざるをえなくなるので、
**実装を始める前に、プランと実物のコードのずれを見つけるための道具**としても効く。

このスキルの成果物は「確かめた図」であって、実装ではない。書き出したらユーザーの確認を待つ。
渡す物は、CSS も図も 1 ファイルに固めた `<資料名>_単一.html`（`<style>`・`<script>`・`<link>` を持たない）と PDF。
隣の `doc.css` と CDN の mermaid を読む HTML は**編集用**で、そのままは渡さない（手順 6）。

## 入力

| 入力 | 取り方 |
|------|-------|
| プラン | 会話の中の承認済みプラン、または `~/.claude/plans/*.md`。図の下書き（mermaid）があればそれを土台にする |
| 層の構成 | プロジェクトの CLAUDE.md・アーキテクチャのルール（例: API → Service → Task / Repository → Model）。box の並びはこの依存の向きに合わせる |
| 見た目の手本 | 前に作ったレイヤー別フローの HTML があれば、その形に合わせる（ユーザーが名指すことが多い） |

## 手順

### 1. プランから図の材料を抜き出す

- 図にする流れ（初回の処理・別の経路・再読み込みや失敗のとき など）を 2〜4 本に分ける。1 本に詰め込まない
- 流れごとに「参加者（層 × ファイル・クラス）」「呼び出しの順番」「新規か変更か既存か」を書き出す
- 既存の経路をそのまま使う流れは、シーケンス図ではなく短い flowchart にしてよい（変わるところだけが分かれば足りる）

### 2. 図にする前に、実物で確かめる

プランに書かれたファイル・クラス・関数・列名を、1 つずつ実物で確かめる。シンボルの探索はプロジェクトの決まり
（Serena・CodeGraph などがあればそれ）に従う。確かめるのは次の 3 つ。

- **在るか**: パス・名前が今のコードと合っているか（移動・改名されていないか）
- **順番**: プランが「A の後に B」と書いているところが、今のコードでも本当にその順か。変えるなら、変える前と後の両方を把握する
- **もう在るもの**: プランが「足す」と書いたものが、実はもう一部入っていないか（引数がもうある・似た経路がある等）

ずれを見つけたら、図はコードの事実に合わせ、**ずれは報告でユーザーに伝える**（勝手にプランを書き換えたことにしない）。
同じ形の実装が別の経路にあれば、その場所（`path:line`）を図の説明文に書いて「これに合わせる」と示す。

### 3. 見た目の部品をそろえる

出力先は既定で `~/.claude/plans/<チケット番号>-<短い名前>/<資料名>.html`（git の外）。
プロジェクトに「資料はリポジトリ内に置く」等の決まりがあればそちらに従う。

CSS と mermaid の初期化は、次の順で探して出力先へ**写す**（相対パスで読むので隣に置く）。

1. ユーザーが名指した手本の HTML のフォルダにある `doc.css` / `doc-mermaid-init.js`
2. プロジェクトの資料用 skill（例: `.claude/skills/doc-authoring/lib/`）にある同名のファイル
3. どちらも無ければ、このスキルの `assets/fallback.css` を `doc.css`、`assets/mermaid-init-fallback.js` を `doc-mermaid-init.js` として写す

### 4. HTML を書く

`assets/template.html` を写して埋める。形は次のとおり。

- **ヘッダー**: タイトル・何をするための資料かの 1〜2 文・`doc-meta` に「更新日」「前提（ユーザーが決めたこと）」「凡例: 【新規】／【変更】／印なしは既存」
- **流れごとの節**: `<h2>図 n. …</h2>` → 図 → キャプション → `<h3>図 n のレイヤーとファイル</h3>` の表（レイヤー／ファイル／クラス・関数／変更）
- **シーケンス図の書き方**
  - 先頭に `%%{init: {"sequence": {"mirrorActors": false, "messageMargin": 16, "boxMargin": 8, "noteMargin": 8, "actorMargin": 18}}}%%` と `autonumber`
  - 層ごとに `box rgb(...) 層の名前 … end` で囲む。隣り合う box は色を交互にして境目を見せる（例: `rgb(250,245,255)` と `rgb(243,232,255)`、外部は `rgb(245,245,245)`）
  - 参加者の名前は「ファイル名またはクラス名＋【新規】【変更】」。長い名前は `<br/>` で折る
  - メッセージにも、変わる呼び出しには【変更】、新しく返す項目には【新規の項目】を付ける
  - 上限時間・再接続など、流れの外の決まりは `Note over` で書く
  - 図の `<pre>` には `class="mermaid doc-seq"` を付ける（横幅を広げる指定をシーケンス図だけに効かせるため。flowchart に効くと図が引き伸ばされて読めなくなる）
- **キャプション**: 図だけでは読めないこと（なぜその順か・何を変えないか）を 2〜3 文。補足は `<span class="doc-figure-src">` に
- 図の無い節を作らない。設計書の一覧などの表は、関係する図の節の `<h3>` にする

mermaid の書き方で落ちやすいところは `references/mermaid-pitfalls.md` にある。図を書き終えたら一度目を通す。

### 5. 描けたかを確かめる

書いただけでは、mermaid の構文エラーや、図が引き伸ばされて読めないことに気づけない。必ず開いて確かめる。

```bash
node ~/.claude/skills/planning-explainer/scripts/render-check.mjs <html の絶対パス> <スクショの出力パス>
```

- プロジェクトのディレクトリで実行する（今の場所から上へ `node_modules/playwright` を探すため）
- 先に `grep -n '{{' <html>` でテンプレートの埋め残しが 0 件であることを確かめる
- 図ごとに `{"svg":true,"err":false}` が出れば描けている。`err:true` や `svg:false` があれば、その図を直す
- スクショ（全ページ）を Read で開き、次を目で見る: 参加者の名前が読める／box の色分けが分かる／flowchart が引き伸ばされていない／表が崩れていない
- playwright が見つからないと言われたら、`--playwright <playwright の index.mjs のパス>` で場所を渡す（プロジェクトの `node_modules/playwright/index.mjs` など）
- プロジェクトに資料の検査スクリプト（図の無い節・リンク切れの検査など）があれば、それも回す。シェル（左ナビ・目次）が無いという指摘は、手本が 1 枚の形なら無視してよい

### 6. 1 枚に固める（渡すのはこちら）

手順 4 の HTML は**編集用**で、隣の `doc.css`・`doc-mermaid-init.js` と CDN の mermaid を読む。フォルダから出すと崩れる。
さらに、CSS と JS を `<style>` / `<script>` で埋め込んだだけの 1 枚も、**Teams・SharePoint のプレビューやメールでは崩れる**
（表示先が `<style>` と `<script>` を取り除くので、スタイルが外れ、mermaid の図も描かれない。2026-10-10 に Teams で実際に崩れた）。
そこで、実ブラウザで描き切った状態を固めた 1 枚と、PDF を作って渡す。

```bash
node ~/.claude/skills/planning-explainer/scripts/bundle.mjs <編集用 HTML> <資料名>_単一.html --pdf <資料名>.pdf
```

- `bundle.mjs` は Chromium で開いて図を描き切り、全要素（図の SVG の中も）の見た目を `style` 属性に書き込み、`<style>`・`<script>`・`<link>` を全部外す。図は描いた後の SVG のまま残る
- プロジェクトのディレクトリで実行する（`render-check.mjs` と同じく `node_modules/playwright` を探す）。描けていない図があれば止まる
- 確かめること（どれも必須）:
  - `check-single.mjs` を回す。その 1 ファイルだけを空のディレクトリに写し、**JavaScript を切ったブラウザ**で開いて、`<style>`・`<script>`・`<link>` が 0 件か・図の SVG の数・全ページのスクショを出す（どれかが外れたら exit 1）。表示先の多くは JS を動かさないので、JS ありで撮っても確かめたことにならない
    ```bash
    node ~/.claude/skills/planning-explainer/scripts/check-single.mjs <資料名>_単一.html <スクショの出力パス> --expect-figures <図の数>
    ```
  - 出たスクショを Read で開き、手順 5 の編集用のスクショと見比べる（文字の色・枠線・【】の詰め・図の文字・box の色分けが同じか）
  - 崩れていたら、編集用と固めた後で同じ要素の `getComputedStyle` を全部突き合わせ、違う性質を `bundle.mjs` の `PROPS`（受け継ぐ性質なら `INHERITED` にも）に足す
- **Teams で渡すなら PDF を勧める。** 固めた HTML は `style` 属性まで消す表示先では崩れうるが、PDF は崩れない

### 7. 渡す

報告は短く、次の 3 つ。

1. 書き出した場所（ユーザーが開けるパス）。**渡す物は `<資料名>_単一.html`（どのブラウザでも 1 ファイルで開ける）と `<資料名>.pdf`（Teams・メール向け）**。編集用の HTML と `doc.css` は直すとき用
2. 確かめたこと（描画・検査の結果、直したところ）
3. **図にする前にコードで分かったこと**（プランとのずれ・もう在ったもの・合わせる手本）

ここで止めて、ユーザーの確認を待つ。確認が取れるまで実装（worktree の作成・コードの変更）を始めない。

## 直すとき

ユーザーに直しを頼まれたら、**編集用の** HTML を直し、手順 5 と手順 6（固め直しと PDF）をもう一度回す。固めた 1 枚を直接直さない（style 属性だらけで直しにくく、次に固め直すと消える）。図の流れ自体が変わるなら、プランとの食い違いが生まれていないかも報告する。
